# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Claude Code plugin (`coddy`) that is also its own single-plugin marketplace. There is no build step and no dependencies: the deliverable is seven prompt files (`skills/*/SKILL.md`), the four sub-agent briefs next to `start`'s, portable Markdown any agent can run as a sub-agent prompt (`skills/start/{implement,harden,review,security}.md`) and the policy file they read first (`skills/start/references/policy.md`), the `coddy` command (`bin/coddy`) and the Claude Code shims under `scripts/` that call it, one hook, one workflow template (`templates/coddy.yml`), and `get.sh`, the installer for other agents and the terminal (`curl … | bash`: clones `main` into `${CODDY_HOME:-~/.coddy}`, or fast-forwards it, and links `bin/coddy` into `${CODDY_BIN:-~/.local/bin}`; `CODDY_REPO_URL` names the repository, which `selftest-core.sh` points at a local bare one).

## Commands

```bash
bash scripts/selftest.sh                    # the shims end to end: both worktree tools, claim, push, guard, tripwire, PR check
bash scripts/selftest-core.sh               # bin/coddy on its CODDY_* inputs alone, with no CLAUDE_* set: root, config paths, guard's ask, config lock, start and ship, the git hooks, `get.sh` and `doctor`
claude plugin validate .                    # manifest + skill frontmatter; its one warning, about this CLAUDE.md, is expected
claude --plugin-dir . -p "/coddy:next"      # run one skill headless against the working copy
```

Both self-tests build a throwaway repo with a local bare remote; `selftest.sh` adds a stub `gh` for the PR check's run block alone and skips the jj leg when `jj` is missing. Run both after any change under `bin/` or `scripts/`. They cannot prove the hooks or skills are wired; check those headless inside an onboarded scratch repo:

- `claude --plugin-dir . -p "start issue 42"` - plain-language trigger. In `-p` the Skill call is denied unless `Skill(coddy:start)` is allowed in settings or via `--allowedTools`.
- `--permission-mode acceptEdits` for edit-guard checks, `--allowedTools Bash` for tripwire checks. Without them the permission layer refuses before any hook runs. For `guard: warn`, have the run quote the hook message back: that is the only proof it reached the model.
- `--plugin-dir` replaces the installed coddy for that run, hooks included, so the installed copy does not need disabling.
- A scratch repo whose `repo` names a repository the GitHub plugin cannot read makes `start` stop at its tracker step: the quick way to see it stop without editing.

Skills act on the project in `$CLAUDE_PROJECT_DIR`, so to exercise one, run `claude --plugin-dir /path/to/coddy` from inside a target project that has (or, for `onboard`, lacks) `.coddy.yml`.

Release = commit straight to `main` (the marketplace installs from it), then bump `version` in `.claude-plugin/plugin.json` as its own commit (`chore: bump to X.Y.Z`). `marketplace.json` carries no version. An installed copy only changes after a bump: `claude plugin marketplace update coddy && claude plugin update coddy@coddy`.

## Architecture

**Prompts hold judgment, scripts hold mechanics.** A skill decides what to do (which issue, branch name, commit message, PR body); anything that is a fixed command sequence lives in a script so it is tested once and pre-approved.

**Shared brief rules live in `skills/start/references/policy.md`.** The four briefs open by reading it: edit scope, open questions, out-of-scope ideas, verify, commit, the common Return lines, the severity rubric and finding format, and the skill map (intent → capability phrase → inline fallback). A skill is routed by what its description says it does, never by name, and only when it is listed for the session; a missing one means the fallback, silently. A new shared rule goes there, not into a brief.

**Core and adapter.** `bin/coddy` holds every mechanic and reads no `CLAUDE_*` variable (`selftest-core.sh` asserts it). Its inputs: `CODDY_ROOT`, where root resolution starts (`$PWD` without it; then `git rev-parse --git-common-dir`, keeping the caller's spelling, and `/.worktrees/*` stripped outside git); `CODDY_SESSION` and `CODDY_PID`, what the lock's owner line records and is compared with (a caller naming none is not held to the owner); `CODDY_AGENT_DIR`, the agent's own directory under the root (no agent-dir rules without it). `scripts/issue.sh`, `config.sh` and `detect.sh` are the Claude Code adapter: shims that map `CLAUDE_PROJECT_DIR`, `CLAUDE_CODE_SESSION_ID` and `CLAUDE_PID` onto those three and set `CODDY_AGENT_DIR=.claude`, always, ignoring any inherited `CODDY_*` value (a `.claude/settings.json` `env` reaches hook environments, so an honoured one could move the root or widen the agent dir; the core itself honours `CODDY_*` when called directly), taking `CLAUDE_PROJECT_DIR`, for the Bash-tool verbs (every verb but the hooks, `config.sh` and `detect.sh` included), only when it is absolute and the working directory is it or under it, compared by real path (that same `env` overrides it in the Bash tool's environment, where the skills and the injected commands run; `PWD` cannot be set from there, and a session opened through a symlink has it in the link's spelling while the project dir is the real one), and as it is for the hooks (`guard`, `snap`, `trip`), which Claude Code spawns with the real one while their working directory follows the Bash tool's `cd`, so held to it a `cd` out of the project would resolve a root with no config and switch every guardrail off, and name `trip`'s snapshot by another root than `snap`'s, and dropping every `GIT_*` but `GIT_AUTHOR_*`, `GIT_COMMITTER_*`, `GIT_SSH*`, `GIT_ASKPASS` and `GIT_TERMINAL_PROMPT` (a `GIT_DIR` from that env resolves the root in another repository, where no config is, and every hook exits 0; the identity, the transport and the credential prompt reach no path), and source the core (sourced, so the core's messages name the shim, as the skills' `allowed-tools` do), which is why `hooks/hooks.json` and every `allowed-tools` line stay as they were. Claude Code puts a plugin's `bin/` on the Bash tool's `PATH`, so `coddy <verb>` runs there too; the skills keep calling the shims. That `bin/` is also a ceiling: claude.ai and Cowork do not install a plugin with a top-level `bin/`, through organisation settings either, so coddy needs the Claude Code CLI. The hook JSON (`warn`'s `additionalContext`, the `ask` on `.coddy.yml`) is Claude Code's format, emitted from the core; later adapters translate it.

**Fact injection.** Each skill opens with `` !`bash "${CLAUDE_PLUGIN_ROOT}/scripts/<x>.sh"` `` blocks. These run at skill load and their stdout is inlined into the prompt, so the model starts with config and repo state rather than discovering them with tool calls. The injected scripts (`config.sh`, `detect.sh`) and `issue.sh status` are read-only, print `key: value` lines, and must not fail loudly (`|| exit 0`, `2>/dev/null`, fallback values) since their output is the prompt. The one injected command that is not read-only is `issue.sh sweep` (`next`, `start`): it fetches `default_branch` and removes what a merged branch left behind, prints `cleaned:` and `kept:` lines, and follows the same rule of never failing loudly. Right under the blocks, each skill carries one fallback line for a host that does not inject or expand (the self-test asserts it on every skill, with its read-by-hand command and its variables): a section showing its command rather than its output means run `coddy config`, `coddy sweep` or `coddy status` (`coddy detect` for `onboard`) by hand and read the output as that section; `${CLAUDE_PLUGIN_ROOT}` left unexpanded means the coddy plugin's own install directory, never a `bin/coddy` or `skills/` found inside the project: `coddy <verb>` in the shim's place, and that directory in a path (the briefs and policy.md `start` hands to sub-agents, the template `onboard` reads); `$issue`, `$onto`, `$base` and `$ARGUMENTS` left unexpanded come from the user's request. The `AGENTS.md` block says the same and names the plugin's repository. The line is written without the injection syntax itself, which Claude Code runs anywhere in a line, not only at its start; the self-test asserts no skill carries it inside a line.

**`bin/coddy` is the only script that mutates** (`scripts/issue.sh` is its shim). `status` prints the root, the config path and the claimed worktrees for the prompts, `config` the config or `NOT_ONBOARDED` and `detect` the onboarding facts, `start` (alias `create`, which the skills call) makes the worktree and installs the git hooks, `claim` locks the issue for this session once the skill has moved it to In Progress, `push` commits and pushes and `ship` runs `verify` first and stops when it fails, `state` records `start`'s phase, review round, upheld disputes, out-of-scope ideas and summary in the lock directory for the owner alone (anyone reads it, `ship` too), `verify` runs the config's verify in the issue's worktree, `diff` prints that worktree's diff against its base (git or jj) and `log` the last commits on given paths on that base (all read-only toward the lock), `sweep` removes the worktree, lock, branch record and local branch of an issue whose PR has merged; `exclude answers|config` puts `$CODDY_AGENT_DIR/coddy` or `.coddy.yml` into git's `info/exclude` unless git ignores it already and `forget answers` removes `$CODDY_AGENT_DIR/coddy/onboard-answers.json` once a config exists (`onboard`'s only shell writes, so its `allowed-tools` holds no path, wildcard, redirect or `rm`: no hook is live before the config, Claude Code splits a `||` rule into subcommands matched one by one and prompts on a `.git/` or `.claude/` write whatever the rule says, and a `*` in a rule is where `rm`'s flags and operands go); `migrate` prints `from:`, `to:`, one `changed:` line per change, `tracked:` (whether git tracks the legacy file) after a move, `legacy:` (`file`, `link`, `dir` or `other`) after a remove and, when the file itself changes, `---` and the migrated file, writing nothing and refusing a `version` above the one it knows, a link or non-file at `.coddy.yml` and a legacy source that is a link; `doctor` prints the install it runs from (`install:`, its real directory through a link or a shim; `via: get.sh` when that is `${CODDY_HOME:-~/.coddy}`, else `other`; `version:` and `commit:`), which needs no project, and, in a project (found as every other verb finds it; a root outside git is one when it holds a config), a line per check, `ok` or the problem with its fix as plain text, exit 1 on any. No config prints `config: none (fix: /coddy:onboard)` and stops; a git dir holding a `commondir` prints `git_dir:` and stops before any git call; then `config` (behind, by `migrate`'s own test, or one `migrate` refuses), `worktree` git or jj, `default_branch` as `origin/<default_branch>` present, `jq`, `git` and, for `worktree: jj`, `jj` on `PATH`, `hooks` as `start` leaves them (`core.hooksPath` coddy's directory, both hooks plain files carrying its header and executable, the coddy path they record an executable file or `coddy` on `PATH`), `pr_check` for `tracker: github` alone (the workflow a plain file identical to `templates/coddy.yml`) and `agents_md` (a plain file, or a link to one, with one `<!-- coddy:begin -->` before one `<!-- coddy:end -->`). It writes and fetches nothing and runs no hook; control characters are dropped from what it prints; `guard`, `snap` and `trip` are the Claude Code hooks and `githook pre-commit|pre-push` the git ones. It reads `worktree` and `default_branch` from the config itself, so the jj/git split lives there and nowhere in the prompts.

**The guardrails are enforced by `hooks/hooks.json`, not by wording.** The layers, all inert until the project is onboarded (the git hooks until `start` installs them, the PR check until its workflow is committed):

- *Edit guard.* `PreToolUse` on Edit/Write/NotebookEdit runs `issue.sh guard`, which rejects (exit 2) any path that is not under `$CODDY_AGENT_DIR/` (`.claude/` from the shims) or inside `.worktrees/<issue>/`, and holds a path inside to that issue's lock (see Lock states). `$CODDY_AGENT_DIR/worktrees/<name>/`, where Claude Code keeps its own worktrees, is the one agent-dir path held to the lock too, or an unclaimed edit could hide there. So "In Progress before any code is edited" and "one issue, one worktree" hold even when no skill fired. `.coddy.yml` at the root gets no sensitive-file prompt from Claude Code, so the guard answers it with `permissionDecision: ask` (exit 0), in both modes, by whatever path the write reaches it: its own spelling or one with `./`, `//` or `..`, a relative path (against the hook's `cwd`), a symlink or hard link from a worktree or the agent dir, any case of its name. With `guard: warn` in the config the same check exits 0 and hands Claude the message as `additionalContext` instead, so both rules become advice; any other value, or no key, blocks. Without `jq` the path cannot be read, so every edit is blocked, in `warn` mode too. The tripwire and the config lock do not read the key, except `snap`'s worktree and push checks.
- *Shell tripwire.* A shell command's writes cannot be predicted from its text, so `PreToolUse` on Bash runs `issue.sh snap` and `PostToolUse` plus `PostToolUseFailure` run `issue.sh trip`. They fingerprint the main checkout (every dirty path with its content hash, `default_branch` when it holds commits its remote branch does not, and `HEAD` when it has left `default_branch`; a detached `HEAD` on that branch's own history is where jj leaves a synced checkout and counts as on it) and exit 2 when the command left new lines in that fingerprint. Only additions count, so an undo is quiet. The fingerprint uses paths rather than git status codes because jj colocation turns untracked files into intent-to-add entries by itself. It also holds one line per git worktree (`git worktree list --porcelain -z`; before git 2.36, which has no `-z`, `--porcelain` line by line, an entry not followed by its `HEAD` or `bare` line taken with the lines up to it, so it holds a line break and is never skipped as coddy's) and jj workspace (`jj workspace list --ignore-working-copy`, its `root` template, from jj 0.38, JSON-escaped) outside `.worktrees/<id>/` and `$CODDY_AGENT_DIR/worktrees/<name>/`, the main checkout aside, so a worktree a command made by any spelling trips, and one that was there before does not. `trip` names each new one's path, whether it is a git worktree or a jj workspace, that `git worktree remove` or `jj workspace forget` removes it once what the directory holds is checked and that `git worktree move` puts back a git worktree moved, renamed or re-created, and `jj workspace rename` a jj workspace at a path `snap` recorded under another name, as plain text: no line is a command to paste, since a command can arrange for one to remove what it did not make. One whose path, git admin id (read from its `.git`, and every one in the common dir's `worktrees/`, so one whose directory was gone is there too) or jj name (every workspace's, one jj lists with no path included) `snap` listed (every worktree's, coddy's included, on fd 3 into the snapshot's `.wt` file, git's as `%q` and jj's as it escapes them, one line each) is reported moved, renamed or re-created, any other made: `trip` hands those records back to the fingerprint (`$seen`), which writes every outside line on fd 4 too, labelled moved when it matches its path (git) or name (jj), kept when it matches only its admin id (git) or path (jj), and made otherwise, and `trip` tells a new line for a worktree's by that label alone, never by its text; a dirty path holding a control character, a quote or a backslash is printed quoted (`q`), so none spans two lines or reads as a worktree's. The hooks run outside Claude Code's sandbox, so no git or jj call in them runs a program a command could plant: root resolution reads the main checkout's git dir without git (walking up from the caller past every `.git` directory that is no repository, as git does (a `HEAD` in either hex case, `objects` and `refs` searchable), the first `.git` up, stopping at git's own root when that is at or above the caller, so what git took is never climbed past, and the root's, which must be a real directory, a link not counting, whichever way the root was found, so a worktree whose own `.git` is garbage and git fails in does not skip it; where git fails, the same walk finds the root instead of stripping `/.worktrees/*`, which stays for a jj workspace with no `.git` at all and as the walk's ceiling, with a start that holds a config itself (a git-less root): the walk never lands on a repository above that, and a link or `commondir` above the project is never odd, and from a `/.worktrees/` path the nearest-repository-with-a-config fallback does not run, so a project nested in another repository, its `.git` renamed, keeps its guard when it holds a config and stays inert when it holds none), and a `commondir` there, which git never writes in a main checkout and the sandbox does not protect, a `.git` that is a link, or a root `.git` that is not a directory, points git at another repository's config (its `core.fsmonitor`) and moves the root, so the root stays the checkout's (for a root `.git` that is a `gitdir:` file elsewhere too, when the checkout holds a config: a session in an absorbed submodule, whose git root under `.git/modules/` holds none, stays inert as git alone left it, while a submodule holding its own config is refused; for a link or `commondir` in a subdirectory holding no config, git's root when that is strictly above it, else the nearest repository above holding one, git failing there included, so the config is found; a root `.git` that is a link, from a linked worktree, leaves the root at the checkout, and a link's message says to remove it) and `guard`, `snap` and `trip` exit 2 before any git call, in either guard mode, `trip` after putting the config back, naming the file to remove by hand (a linked worktree's own `commondir` is by design); and none runs inside a worktree a command could have made: the main checkout's `git status` runs with `--ignore-submodules=dirty`, so git runs nothing in a submodule, though it reads the submodule's config (`.git/modules/<name>/config`, which the sandbox does not protect), whose `core.fsmonitor` could name a program, and `jj workspace list` with `--no-pager` and `--ignore-working-copy`, which also skips the import that could sign a commit. One under those directories is coddy's only while a real directory sits at its physical path: one moved out (by `mv` or `git worktree move`), or reached there through a link, is listed, so the command that moves or deletes it trips once. Every path and name is printed in single quotes (`'\''` for a quote, never `printf %q`, whose bare mid-word `~` zsh's `extendedglob` reads as a glob operator), a backslash as `\134` and its control characters (C0, DEL, C1) as `\ooo`, so none reads as a second entry or as another entry's spelling. One whose path or name holds a control character, a quote or a backslash is never skipped as the root or coddy's own: only what follows the root is held to that test before the skip (the root as jj escapes it, for jj), so a project whose own path holds such a character does not trip on `start`. Before the command runs, `snap` (after writing the snapshot, so `trip` finds it) reads `tool_input.command` with `adds`, which tokenises it in awk as the shell would, in time linear in its length (quotes, backslashes, comments, redirections, heredoc bodies; a `$(` or backtick substitution, quoted or not, read as commands of its own and as one word it cannot fix in the command around it, whose words after it stay there, a backtick one ending at the first backtick no backslash escapes, whatever quotes it crosses, and one still open at the end of the text closed there; a heredoc fed to a shell, `sh`, `bash`, `dash`, `ksh` or `zsh` reading its script from stdin, read in place as commands, however deep, in the directory at that point, a `cd` in it kept to it; segments on `;`, `&`, `|`, `(`, `)` and line breaks; `VAR=value` prefixes, reserved words and the `env`, `command`, `builtin`, `exec`, `nohup`, `time`, `timeout`, `nice` and `xargs` wrappers skipped, each option that takes a value with it and `timeout`'s duration, `env -C` followed, and among them a word of unquoted substitutions alone, which may expand to nothing and bash then drops, so the word after it is read as the command, as is a command name past the unquoted substitutions it starts with, and either passes with a note when it cannot be fixed either; `git`, `jj`, `git-push` and `git-send-pack` in any case, as a case-insensitive file system runs them, the last two by any path; a literal `cd`/`pushd` followed, undone at a subshell's parenthesis and unknown after a `popd` or when reached past such a word or substitution, which may print the command bash runs in its place, and `git -C`; each git and jj option that takes a value skipped with it) and prints where each `git worktree add` and `jj workspace add` would put its worktree, resolved against the hook's `cwd` (`abspath`: `..` collapsed by name, the existing part physical); one outside those directories exits 2 naming `/coddy:start <issue>`, `guard: warn` turns that into `additionalContext`. It is the one function another check of a command's text extends (its `run`): its `push` reads a `git push`, `git send-pack` or `jj git push` by its own options (git's long ones by any prefix, as git takes them, each undone by a later `--no-` form, `--no-force-with-lease` every lease and `--no-mirror` a `git push -f` too; the first word after them is the repository, `--repo` or not, or send-pack's URL; `tag <name>` names a tag; under the command's own `-c help.autocorrect`, a subcommand one edit from `push` is one), prints nothing for a dry run, `-h` or `--help`, or git's own `-v` or `--version` before the subcommand, which push nothing, and `snap` refuses, naming `/coddy:ship`, a push to `default_branch` (a refspec's destination, `refs/heads/` or `heads/` stripped, or, quoted with a `*`, a pattern matched against `refs/heads/<default_branch>`; `HEAD`, `@` and a git push with no refspec read as the branch checked out where the command runs, from the `HEAD` of the repository git finds from there (at each level up, a `.git` that is a `gitdir:` file, or else a `.git` that is a repository, or else the directory itself as a bare one: a `HEAD` git takes, and `objects` and `refs`, through a `commondir` file when there is one; git walks past any other), or in the git dir `--git-dir` or `GIT_DIR` names, every file read as data, bounded, trimmed as git trims it, a link `HEAD` as the ref it names, and never by git; a push with no refspec otherwise by the command's own `-c remote.<name>.push` refspecs, and as every branch under its `-c push.default=matching` and for a send-pack, which matches; `--all`, `--mirror`, `--branches`, `:`, and jj's `--all` and `--tracked`, as every branch; jj's `-b`, `exact:` stripped, and `--named`'s name), and, as a person's to make, every force push (`-f`, `--force`, `--force-with-lease`, a `+` refspec), the issue's own branch included, and every remote branch delete (`-d`, `--delete`, `--prune`, `--mirror`, an empty source, jj's `--deleted`); `jj git push -c` passes. It fails open, saying so in `additionalContext`: a word it cannot fix (`$var`, a backtick, a glob, a brace, `~`, a line break, after a `cd` it cannot follow; for a push, a jj pattern other than `exact:`, a bare `jj git push` or one with `-r` alone, whose bookmarks only jj knows, a repository word it cannot fix with no refspec after it, which may split into some, any push under `xargs`, whose input may add some, `send-pack --stdin`, a `cd` into no directory, which leaves the shell where it was, a git dir that is no repository, a `commondir` that is no plain file, and a `HEAD` naming no branch git could have, a reftable repository's stub included), and no `jq` (a fixed message, only when the payload names a worktree, a workspace or a push); not onboarded, it is inert like every hook.
- *Config lock.* The config is the off switch for all of the above, so `snap` keeps a copy of both its paths, `.coddy.yml` and the legacy `.claude/coddy.yml`, present or not, and `trip` puts each back when a shell command deleted or changed it, and removes a `.coddy.yml` the command made next to a live `.claude/coddy.yml`, which it would shadow. A link that was not there or points elsewhere, or a directory, in a config's place is a change whatever it holds (a link reaches a file the lock does not watch); a link the user keeps there, as it was, is not, and its content is compared through it. What `trip` puts back is a plain file, and when that write fails it says so and keeps the copy under `TMPDIR` rather than reporting the file restored; nothing under `TMPDIR` is opened unless it is a plain file, so a FIFO a command plants at a snapshot name cannot hang it, and `snap` makes every record a new file (`set -C`, `O_EXCL`), the config's before the fingerprint's git calls, so a link a command plants at a snapshot name is never written through: the write fails, `snap` drops the snapshot and `trip` reports it lost. A change that came through git, a pull of a shared config or a checkout, is put back the same way: nothing a shell command run as the same user can write (a ref, a loose object, a replace object, a git config, the remote's URL) tells it from a forged one, so `trip` trusts only the snapshot it wrote and names `/coddy:config` in its message, which shows the diff against `HEAD` and, on the user's yes, writes `HEAD`'s copy with the Write tool, where the guard's `ask` applies. The restored file then differs from `HEAD`, so the fingerprint leaves both config paths to the lock rather than reporting them as the command's change, and `default_branch` is read from the snapshot's copy of the config rather than the one the command left. Once `.coddy.yml` is live (settled first by `trip`), the legacy file is ignored and cannot change the effective config, so the lock lets it go: a shell delete or change of it is not put back, which is how `/coddy:migrate` ends the move, or removes a leftover, with `rm .claude/coddy.yml`. While the legacy file is the only config, the lock restores it as it does `.coddy.yml`. Legitimate changes go through the Edit tool (`/coddy:config`), where the guard's `ask` (`.coddy.yml`) or Claude Code's own sensitive-file prompt (`.claude/coddy.yml`) asks the user. `trip` keys off the snapshot, never off the config, or a deleted config would silence it: `snap` writes one before every command, holding `NOT_ONBOARDED` alone while no config is, so a command that left no snapshot, or one without its copy of the config, is rejected as one that touched it, and a command run outside the workflow, the one that writes the config included (a pull of a shared `.coddy.yml` into a fresh clone), is let through; leaving the workflow by hand is removing the config.
- *Git hooks.* `start` (`create`, on a new worktree or an existing one) writes `.git/hooks/coddy/pre-commit` and `pre-push`, each running `coddy githook` through the absolute path of the `bin/coddy` that wrote them (so `start` refuses to run from stdin), else `coddy` on `PATH`, else refusing, naming `/coddy:start <issue>`, `--no-verify` and the command that puts the recorded `core.hooksPath` back (`git config --unset core.hooksPath` when none was), and sets `core.hooksPath` to that directory by its absolute path, since git resolves a relative one per worktree; an absolute value naming it by any spelling (`-ef`, a root reached through a symlink) counts as set. The `core.hooksPath` it replaces, none included, is recorded in `.git/config` as `coddy.previousHooksPath` whenever it is not coddy's, so a rerun keeps the record and a hook manager that re-set it is undone by the next `start`. git runs hooks outside Claude Code's sandbox, which therefore keeps every write out of `.git/hooks` and `.git/config`: whatever a hook runs is named in one of the two (`bin/coddy` lives outside the project), never anywhere a sandboxed command could rewrite it, and `githook` reads `.git/coddy` (branch records, locks) only as data, so forging it gets no further than `--no-verify`. `start` writes a hook only when its content would change, and `.git/config` only when the value would, so a rerun with nothing to change passes inside the sandbox; a write that fails with `Operation not permitted` names the sandbox and the one `start` the user runs from their own terminal, any other failure shows its own error. Then it runs the previous hook of the same name, its directory read from `.git/config` alone (`.git/hooks/` when none was set), with the same arguments and stdin, its exit the hook's; not onboarded, that hook alone. The hook unsets `CODDY_ROOT`: git runs it at the top of the worktree, where the root is found, its `GIT_DIR` included.
- *Branch protection.* `onboard` asks whether `default_branch` requires a pull request and, when it does not, says what to set by hand (no MCP tool reads or writes protection). It is the only layer that holds when a command edits, commits and pushes to `default_branch` in one go.
- *PR check.* `templates/coddy.yml`, which `onboard` writes to `.github/workflows/coddy.yml` on a GitHub tracker without asking (a differing copy backed up first) and says to require on `default_branch`, fails a PR that closes no issue, or closes one that is closed or has no assignee (job name `closes a claimed issue`). Open and assigned is the remote invariant from `claim` to the merge, since `ship` removes the `in progress` label the moment the PR opens and the check runs again on every push. Keyed on the closing references rather than the branch name, it is the only layer that ties a PR to its issue for a cloud agent, which never runs coddy and names its own branch. GitHub computes those references only for a PR against its default branch, so on a PR whose base is another branch (a stack) the block falls back to the closing keywords in the PR body and looks each issue up itself. The run block reads owner, repo, PR number, base, default branch and body from `env`, so it is plain shell that the self-test extracts and runs against the stub `gh`.

**Lock states.** `claim` makes the lock `.git/coddy/<issue>/` with `mkdir`, so of two sessions claiming at once one wins, and writes its `owner` file: `<CODDY_SESSION> <CODDY_PID> <start>`, the first two from `CLAUDE_CODE_SESSION_ID` and `CLAUDE_PID`, which Claude Code sets in every shell command's environment and the shims pass on, the last that process's start time from `ps -o lstart=` (spaces as `_`; empty without `ps`). The editing session is the hook payload's `session_id`. Mine means the same session id or the same pid, since `/clear` changes the id and not the process and `--resume` the process and not the id. A pid counts only while it is the process that started at `<start>`: a reused pid with another start time reads as gone, and a line without a start time, or one `ps` cannot check, falls back to the pid alone. What each script does with an issue's lock:

| Lock | `guard` (edit in its worktree) | `claim` | `push` | `sweep` (merged) | `status` owners |
|---|---|---|---|---|---|
| none | rejects: not In Progress | makes it (needs the worktree) | refuses | skips | not listed |
| mine | allows, moves the owner line to the current id and pid | no-op, moves the owner line | allows | cleans | `me` |
| another session, pid runs | rejects, naming the owner | refuses; `--take` takes it | refuses | keeps (`kept:`) | `<id> (running)` |
| another session, pid gone | rejects, naming the owner as not running | takes it on the spot | refuses | cleans | `<id> (gone)` |
| in flight: directory, no `owner` line | rejects | refuses; `--take` takes it | allows | cleans | `unknown` |
| marker from before locks (plain file) | allows | replaces it with a lock | allows | cleans | `unknown` |

A caller that names no session (a hook payload without `session_id`, a script run by hand) is not held to the owner, and neither is a lock whose owner line names none (a `claim` run by hand): `guard` and `push` allow, `status` says `unknown`, and `claim` reads its pid as in the rows above. Moving the owner line on the owner's edit or re-claim leaves no dead pid behind for another session to take over. `/coddy:start <issue>` is the remedy every rejection names; it runs `claim --take` only after asking the user.

**`allowed-tools` must mirror the commands exactly.** Every injected command, and every `issue.sh` subcommand a skill runs, is repeated in that skill's `allowed-tools` frontmatter as `Bash(bash "${CLAUDE_PLUGIN_ROOT}/scripts/<x>.sh" …)`. Adding, renaming, or re-quoting one without updating that line brings back permission prompts on every skill run.

**Onboarding gate.** `.coddy.yml` at the target project's root is the plugin's config; `.claude/coddy.yml`, where earlier versions wrote it, is read while `.coddy.yml` is absent, and `issue.sh status` prints which as `config`. The config's `version` key names its schema (absent is 0, the layout from before `.coddy.yml`); `/coddy:migrate` moves it up: `issue.sh migrate` prints the steps it would take and the migrated file, read-only, and the skill backs up the source under `.claude/coddy/backup/<ts>/`, writes `.coddy.yml` with the Write tool, where the guard asks, and removes the legacy file. `config` warns on a behind config and still applies the change, and refuses to touch `version`; the next schema change is one more step function in `bin/coddy` and the version bumped in the three schema copies. `scripts/config.sh` prints it, or the sentinel `NOT_ONBOARDED`; every skill except `onboard` injects it and stops on the sentinel, and the guard does nothing without it. `onboard` instead injects `scripts/detect.sh` (the root, which every path it writes is spelled from, since the session may be open in a subdirectory, both config paths, remote, whether `jj` and `jq` are installed, `os` and `pkg`, the first of brew, apt-get, dnf and winget on `PATH`, which keys its install commands, default branch, what is at the PR check workflow's path as `pr_check`: `none`, `present`, `symlink` for a link at `.github`, `.github/workflows` or the file, `dir` or another kind, what is at `AGENTS.md` as `agents_md`: `absent`, `file`, `symlink` for a link whether or not it reaches a file, `dir` or another kind, make/npm targets, roadmap, whether `.coddy.yml` is git-ignored, recent commits and branches) and runs as a wizard of seven steps, `checks → tracker → branch → verify → tiers → AGENTS.md → review`, an agenda strip before each and at most one question call per step with the recommended option first. Answers are saved as given in `.claude/coddy/onboard-answers.json`, keyed by step with the detect facts the step keyed on, so a re-run shows them and asks only the steps unanswered or whose facts changed; the file goes once the config is written. **Config schema has three copies.** The annotated schema in `skills/onboard/SKILL.md` is authoritative; `skills/config/SKILL.md` lists the same keys with their validation rules, and `README.md` shows an example; the self-test fails unless all three name the same keys. Adding a key means updating all three, `detect.sh` if it can be inferred, and every skill or script that should read it. `onboard` creates the file; `config` changes single keys afterwards and refuses to switch `worktree` while an issue worktree exists. `onboard` never asks for `guard`, `review_block` or `review_rounds`, and asks `tiers` for the running agent only; `config` sets `guard`, and sets `warn` only on the user's explicit ask.

**Tracker variants stay in the prompts.** Tracker is `github` (GitHub MCP plugin tools) or `jira` (Atlassian MCP plugin tools): MCP tools, not CLIs, so no script reaches either, every tracker read or write is a step in a skill, and `bin/coddy` holds only local mechanics. A step that touches the tracker spells out both variants inline.

**Issue work lives in `.worktrees/<issue>`.** The directory name is the issue id, which is how `ship` and the guard find the issue. `start <issue> <branch> [base-issue]` (`create` in the skills) starts the branch from `default_branch` on the remote, or from the base issue's recorded branch as it stands locally (`/coddy:start <issue> onto <base-issue>`), recording that base in `.git/coddy/<issue>.base`; `issue.sh status` prints it as `bases` and `ship` makes it the PR's `--base`, so a stacked PR shows only its own diff. `issue.sh status` lists only the directories that have a claim lock, so a worktree coddy did not create is never offered to `ship` and stays uneditable. It also prints each claim's owner as `owners` (`me`, another session's id with whether its pid runs, or `unknown` for a marker without one), which `next` reads to set claimed issues aside and `ship` to pick only this session's. Every script resolves the real project root when the session was opened inside a worktree, and `issue.sh status` prints it as `root` for the prompts. `worktree` is `git` (the default, also when the key is absent at version 2) or `jj`; below version 2 an absent or empty key means `jj`, which migrate pins as `worktree: jj`. A jj workspace has `.jj/` and no `.git/`, so `push` drives it with `jj` and the PR is opened by branch name from the skill.

**`start` order is local first, tracker second.** The worktree is created before the issue is claimed, so a failed fetch or a missing `jj` never leaves an issue In Progress with no branch; `claim` refuses to run without the worktree. A re-claim runs the tracker step again, which is idempotent. For either tracker, `start` reads the issue before the transition and refuses one assigned to someone else, or in progress and not to the caller, naming who has it, on a re-claim too, so a takeover from another machine is caught; on the user's yes it reassigns the issue itself and names who lost it, and `claim` records the result.

**In Progress ends at the PR.** `in progress` means no PR yet: `ship` takes the label off (Jira: In Review) once the PR is open, and `start` on a branch with an open PR assigns the issue without the label, since the PR check reads the assignee, and `claim` records it. `sweep` ends the local side once the worktree's last commit is in `default_branch` on the remote through a merge commit, or as the same patches through a squash or rebase merge (git alone, no tracker, and a worktree still on `default_branch`'s own first-parent line is one with nothing of its own yet) and nothing is uncommitted, and only when its lock does not name another running session.

**Skills must stay model-invocable.** None may set `disable-model-invocation` (the self-test asserts it); each carries a `when_to_use` line of trigger phrases so it fires from plain language as well as `/coddy:<name>`. `ship` is the exception in tone: its `when_to_use` restricts it to explicit asks. Keep frontmatter values free of `: ` and ` #` (unquoted YAML scalars).

Skill flow is `onboard` → `next` → `start <issue>` → `ship`, with `triage` feeding new issues back into the tracker and `config` and `migrate` beside it. `start` runs from the claim to a reviewed diff in one command: context, thinking with the user, one plan approval with the tier inside it, then implementer, two hardening passes and the code and security review loop, as sub-agents on the briefs next to it (the main agent follows them itself without sub-agents); re-running it resumes from the latest `<!-- coddy:plan -->` comment and `issue.sh state`, and headless questions are posted as a `<!-- coddy:questions -->` issue comment and answered in later comments. Each skill ends by naming the next command rather than chaining into it, and each states what it must not do (`ship` never merges or fixes failures; `onboard` writes nothing but the config, the PR check workflow, the `AGENTS.md` block, its `.git/info/exclude` lines and its own answers and backups under `.claude/coddy/`, and installs nothing but `jq` and `jj`, each through a Bash call the user allows).

## Conventions

- A hook blocks only on exit 2; any other non-zero exit is a non-blocking error. Hook paths in `bin/coddy` set `code=2` before `die`.
- `bin/coddy` reads no `CLAUDE_*` variable and names no Claude Code path but the legacy config and, for `doctor`'s `version:`, `.claude-plugin/plugin.json`, the repository's one version source; anything Claude-specific goes in the shims under `scripts/`.
- A Bash command that exits non-zero fires `PostToolUseFailure`, not `PostToolUse`, so `trip` is registered on both.
- A hook that lets the call through but has something to tell Claude prints `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "additionalContext": "..."}}` and exits 0. It leaves `permissionDecision` out, so the normal permission flow still applies.
- `${CLAUDE_PLUGIN_ROOT}` is expanded in skill bodies and in `allowed-tools`, so skills call scripts by that path.
- Scripts are committed executable (`chmod +x`).
- Skill bodies are terse imperative checklists: `condition → action` guards up top, numbered steps, per-tracker variants as sub-bullets. Match that style rather than writing explanatory prose.
- Commits: `type: summary` (`feat`, `fix`, `chore`).
