# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Claude Code plugin (`coddy`) that is also its own single-plugin marketplace. There is no build step and no dependencies: the deliverable is six prompt files (`skills/*/SKILL.md`), the four sub-agent briefs next to `start`'s, portable Markdown any agent can run as a sub-agent prompt (`skills/start/{implement,harden,review,security}.md`), the `coddy` command (`bin/coddy`) and the Claude Code shims under `scripts/` that call it, one hook, and one workflow template (`templates/coddy.yml`).

## Commands

```bash
bash scripts/selftest.sh                    # the shims end to end: both worktree tools, claim, push, guard, tripwire, PR check
bash scripts/selftest-core.sh               # bin/coddy on its CODDY_* inputs alone, with no CLAUDE_* set: root, config paths, guard's ask, config lock, start and ship
claude plugin validate .                    # manifest + skill frontmatter; its one warning, about this CLAUDE.md, is expected
claude --plugin-dir . -p "/coddy:next"      # run one skill headless against the working copy
```

Both self-tests build a throwaway repo with a local bare remote; `selftest.sh` adds a stub `gh` for the PR check's run block alone and skips the jj leg when `jj` is missing. Run both after any change under `bin/` or `scripts/`. They cannot prove the hooks or skills are wired; check those headless inside an onboarded scratch repo:

- `claude --plugin-dir . -p "start issue 42"` - plain-language trigger. In `-p` the Skill call is denied unless `Skill(coddy:start)` is allowed in settings or via `--allowedTools`.
- `--permission-mode acceptEdits` for edit-guard checks, `--allowedTools Bash` for tripwire checks. Without them the permission layer refuses before any hook runs. For `guard: warn`, have the run quote the hook message back: that is the only proof it reached the model.
- `--plugin-dir` replaces the installed coddy for that run, hooks included, so the installed copy does not need disabling.
- A scratch repo whose `repo` names a repository the GitHub plugin cannot read makes `start` stop at its tracker step: the quick way to see it stop without editing.

Skills act on the project in `$CLAUDE_PROJECT_DIR`, so to exercise one, run `claude --plugin-dir /path/to/coddy` from inside a target project that has (or, for `onboard`, lacks) `.coddy.yml`.

Release = commit straight to `main` (the marketplace installs from it), then bump `version` in `.claude-plugin/plugin.json` as its own commit (`chore: bump to X.Y.Z`). `marketplace.json` carries no version. An installed copy only changes after a bump: `claude plugin marketplace update coddy && claude plugin update coddy@coddy`.

## Architecture

**Prompts hold judgment, scripts hold mechanics.** A skill decides what to do (which issue, branch name, commit message, PR body); anything that is a fixed command sequence lives in a script so it is tested once and pre-approved.

**Core and adapter.** `bin/coddy` holds every mechanic and reads no `CLAUDE_*` variable (`selftest-core.sh` asserts it). Its inputs: `CODDY_ROOT`, where root resolution starts (`$PWD` without it; then `git rev-parse --git-common-dir`, keeping the caller's spelling, and `/.worktrees/*` stripped outside git); `CODDY_SESSION` and `CODDY_PID`, what the lock's owner line records and is compared with (a caller naming none is not held to the owner); `CODDY_AGENT_DIR`, the agent's own directory under the root (no agent-dir rules without it). `scripts/issue.sh`, `config.sh` and `detect.sh` are the Claude Code adapter: shims that map `CLAUDE_PROJECT_DIR`, `CLAUDE_CODE_SESSION_ID` and `CLAUDE_PID` onto those three and set `CODDY_AGENT_DIR=.claude`, always, ignoring any inherited `CODDY_*` value (a `.claude/settings.json` `env` reaches hook environments, so an honoured one could move the root or widen the agent dir; the core itself honours `CODDY_*` when called directly) and dropping every `GIT_*` but `GIT_AUTHOR_*`, `GIT_COMMITTER_*`, `GIT_SSH*`, `GIT_ASKPASS` and `GIT_TERMINAL_PROMPT` (a `GIT_DIR` from that env resolves the root in another repository, where no config is, and every hook exits 0; the identity, the transport and the credential prompt reach no path), and source the core (sourced, so the core's messages name the shim, as the skills' `allowed-tools` do), which is why `hooks/hooks.json` and every `allowed-tools` line stay as they were. Claude Code puts a plugin's `bin/` on the Bash tool's `PATH`, so `coddy <verb>` runs there too; the skills keep calling the shims. That `bin/` is also a ceiling: claude.ai and Cowork do not install a plugin with a top-level `bin/`, through organisation settings either, so coddy needs the Claude Code CLI. The hook JSON (`warn`'s `additionalContext`, the `ask` on `.coddy.yml`) is Claude Code's format, emitted from the core; later adapters translate it.

**Fact injection.** Each skill opens with `` !`bash "${CLAUDE_PLUGIN_ROOT}/scripts/<x>.sh"` `` blocks. These run at skill load and their stdout is inlined into the prompt, so the model starts with config and repo state rather than discovering them with tool calls. The injected scripts (`config.sh`, `detect.sh`) and `issue.sh status` are read-only, print `key: value` lines, and must not fail loudly (`|| exit 0`, `2>/dev/null`, fallback values) since their output is the prompt. The one injected command that is not read-only is `issue.sh sweep` (`next`, `start`): it fetches `default_branch` and removes what a merged branch left behind, prints `cleaned:` and `kept:` lines, and follows the same rule of never failing loudly.

**`bin/coddy` is the only script that mutates** (`scripts/issue.sh` is its shim). `status` prints the root, the config path and the claimed worktrees for the prompts, `config` the config or `NOT_ONBOARDED` and `detect` the onboarding facts, `start` (alias `create`, which the skills call) makes the worktree, `claim` locks the issue for this session once the skill has moved it to In Progress, `push` commits and pushes and `ship` runs `verify` first and stops when it fails, `state` records `start`'s phase, review round, upheld disputes, out-of-scope ideas and summary in the lock directory for the owner alone (anyone reads it, `ship` too), `verify` runs the config's verify in the issue's worktree, `diff` prints that worktree's diff against its base (git or jj) and `log` the last commits on given paths on that base (all read-only toward the lock), `sweep` removes the worktree, lock, branch record and local branch of an issue whose PR has merged; `guard`, `snap` and `trip` are the hooks. It reads `worktree` and `default_branch` from the config itself, so the jj/git split lives there and nowhere in the prompts.

**The guardrails are enforced by `hooks/hooks.json`, not by wording.** The layers, all inert until the project is onboarded (the PR check until its workflow is committed):

- *Edit guard.* `PreToolUse` on Edit/Write/NotebookEdit runs `issue.sh guard`, which rejects (exit 2) any path that is not under `$CODDY_AGENT_DIR/` (`.claude/` from the shims) or inside `.worktrees/<issue>/`, and holds a path inside to that issue's lock (see Lock states). `$CODDY_AGENT_DIR/worktrees/<name>/`, where Claude Code keeps its own worktrees, is the one agent-dir path held to the lock too, or an unclaimed edit could hide there. So "In Progress before any code is edited" and "one issue, one worktree" hold even when no skill fired. `.coddy.yml` at the root gets no sensitive-file prompt from Claude Code, so the guard answers it with `permissionDecision: ask` (exit 0), in both modes, by whatever path the write reaches it: its own spelling or one with `./`, `//` or `..`, a relative path (against the hook's `cwd`), a symlink or hard link from a worktree or the agent dir, any case of its name. With `guard: warn` in the config the same check exits 0 and hands Claude the message as `additionalContext` instead, so both rules become advice; any other value, or no key, blocks. Without `jq` the path cannot be read, so every edit is blocked, in `warn` mode too. The tripwire and the config lock do not read the key.
- *Shell tripwire.* A shell command's writes cannot be predicted from its text, so `PreToolUse` on Bash runs `issue.sh snap` and `PostToolUse` plus `PostToolUseFailure` run `issue.sh trip`. They fingerprint the main checkout (every dirty path with its content hash, `default_branch` when it holds commits its remote branch does not, and `HEAD` when it has left `default_branch`; a detached `HEAD` on that branch's own history is where jj leaves a synced checkout and counts as on it) and exit 2 when the command left new lines in that fingerprint. Only additions count, so an undo is quiet. The fingerprint uses paths rather than git status codes because jj colocation turns untracked files into intent-to-add entries by itself.
- *Config lock.* The config is the off switch for all of the above, so `snap` keeps a copy of both its paths, `.coddy.yml` and the legacy `.claude/coddy.yml`, present or not, and `trip` puts each back when a shell command deleted or changed it, and removes a `.coddy.yml` the command made next to a live `.claude/coddy.yml`, which it would shadow. A link that was not there or points elsewhere, or a directory, in a config's place is a change whatever it holds (a link reaches a file the lock does not watch); a link the user keeps there, as it was, is not, and its content is compared through it. What `trip` puts back is a plain file, and when that write fails it says so and keeps the copy under `TMPDIR` rather than reporting the file restored; nothing under `TMPDIR` is opened unless it is a plain file, so a FIFO a command plants at a snapshot name cannot hang it. A change that came through git, a pull of a shared config or a checkout, is put back the same way: nothing a shell command run as the same user can write (a ref, a loose object, a replace object, a git config, the remote's URL) tells it from a forged one, so `trip` trusts only the snapshot it wrote and names `/coddy:config` in its message, which shows the diff against `HEAD` and, on the user's yes, writes `HEAD`'s copy with the Write tool, where the guard's `ask` applies. The restored file then differs from `HEAD`, so the fingerprint leaves both config paths to the lock rather than reporting them as the command's change, and `default_branch` is read from the snapshot's copy of the config rather than the one the command left. Once `.coddy.yml` is live (settled first by `trip`), the legacy file is ignored and cannot change the effective config, so the lock lets it go: a shell delete or change of it is not put back, which is how `/coddy:config` ends the move with `rm .claude/coddy.yml`. While the legacy file is the only config, the lock restores it as it does `.coddy.yml`. Legitimate changes go through the Edit tool (`/coddy:config`), where the guard's `ask` (`.coddy.yml`) or Claude Code's own sensitive-file prompt (`.claude/coddy.yml`) asks the user. `trip` keys off the snapshot, never off the config, or a deleted config would silence it: `snap` writes one before every command, holding `NOT_ONBOARDED` alone while no config is, so a command that left no snapshot, or one without its copy of the config, is rejected as one that touched it, and a command run outside the workflow, the one that writes the config included (a pull of a shared `.coddy.yml` into a fresh clone), is let through; leaving the workflow by hand is removing the config.
- *Branch protection.* `onboard` asks whether `default_branch` requires a pull request and, when it does not, says what to set by hand (no MCP tool reads or writes protection). It is the only layer that holds when a command edits, commits and pushes to `default_branch` in one go.
- *PR check.* `templates/coddy.yml`, which `onboard` offers to copy to `.github/workflows/coddy.yml` and to require on `default_branch`, fails a PR that closes no issue, or closes one that is closed or has no assignee (job name `closes a claimed issue`). Open and assigned is the remote invariant from `claim` to the merge, since `ship` removes the `in progress` label the moment the PR opens and the check runs again on every push. Keyed on the closing references rather than the branch name, it is the only layer that ties a PR to its issue for a cloud agent, which never runs coddy and names its own branch. GitHub computes those references only for a PR against its default branch, so on a PR whose base is another branch (a stack) the block falls back to the closing keywords in the PR body and looks each issue up itself. The run block reads owner, repo, PR number, base, default branch and body from `env`, so it is plain shell that the self-test extracts and runs against the stub `gh`.

Known ceilings: the tripwire reports after the fact and does not see background commands or shell writes inside any worktree, unclaimed or another session's, so only the edit guard (Edit/Write/NotebookEdit) and `push` are held to the lock's owner; both hold only when the lock and the caller name a session, so a claim, a hook payload or a push without one (a script run by hand) is not held to it; both trackers are MCP tools, so the lock records the transition the skill made rather than verifying it, and the skill reads the issue before it writes it, so two machines claiming inside the same round trip both succeed; `sweep` tells a squash or rebase merge by patch id, so one whose conflicts were resolved upstream leaves its worktree in place until removed by hand; the PR check reads a stacked PR's closing keywords from its body, so a sidebar-only link on a PR against another branch is not seen; the GitHub MCP plugin sets an issue's labels only as a whole list, so `start` adding `in progress` and `ship` removing it each read the labels and write the list back, and a label someone adds in between is dropped; `start`'s sub-agents run in the parent's process and session, so the lock and the guard cannot tell them apart from the parent: a sub-agent's edit counts as the session's own; the Review section `ship` writes is self-reported: any command in the owning session can set `state` to done, so it records what start did, not a guardrail; the snapshot under `TMPDIR` is within reach of a shell command run as the same user, so one that rewrites it as a project's outside the workflow and removes the config with it is not seen; the fingerprint reads `refs/remotes/origin/<default_branch>` as it stands, so a command that writes that ref hides a commit on `default_branch` from the tripwire, which branch protection catches at the push.

**Lock states.** `claim` makes the lock `.git/coddy/<issue>/` with `mkdir`, so of two sessions claiming at once one wins, and writes its `owner` file: `<CODDY_SESSION> <CODDY_PID> <start>`, the first two from `CLAUDE_CODE_SESSION_ID` and `CLAUDE_PID`, which Claude Code sets in every shell command's environment and the shims pass on, the last that process's start time from `ps -o lstart=` (spaces as `_`; empty without `ps`). The editing session is the hook payload's `session_id`. Mine means the same session id or the same pid, since `/clear` changes the id and not the process and `--resume` the process and not the id. A pid counts only while it is the process that started at `<start>`: a reused pid with another start time reads as gone, and a line without a start time, or one `ps` cannot check, falls back to the pid alone. What each script does with an issue's lock:

| Lock | `guard` (edit in its worktree) | `claim` | `push` | `sweep` (merged) | `status` owners |
|---|---|---|---|---|---|
| none | rejects: not In Progress | makes it (needs the worktree) | refuses | skips | not listed |
| mine | allows, moves the owner line to the current id and pid | no-op, moves the owner line | allows | cleans | `me` |
| another session, pid runs | rejects, naming the owner | refuses; `--take` takes it | refuses | keeps (`kept:`) | `<id> (running)` |
| another session, pid gone | rejects, naming the owner as not running | takes it on the spot | refuses | cleans | `<id> (gone)` |
| in flight: directory, no `owner` line | rejects | refuses; `--take` takes it | allows | cleans | `unknown` |
| marker from before locks (plain file) | allows | replaces it with a lock | allows | cleans | `unknown` |

A caller that names no session (a hook payload without `session_id`, a script run by hand) is not held to the owner, and neither is a lock whose owner line names none (a `claim` run by hand): `guard` and `push` allow, `status` says `unknown`, and `claim` reads its pid as in the rows above. Moving the owner line on the owner's edit or re-claim leaves no dead pid behind for another session to take over. `/coddy:start <issue>` is the remedy every rejection names; it runs `claim --take` only after asking the user.

**`allowed-tools` must mirror the commands exactly.** Every injected command, and every `issue.sh` subcommand a skill runs, is repeated in that skill's `allowed-tools` frontmatter as `Bash(bash "${CLAUDE_PLUGIN_ROOT}/scripts/<x>.sh" …)`. Adding, renaming, or re-quoting one without updating that line brings back permission prompts on every skill run.

**Onboarding gate.** `.coddy.yml` at the target project's root is the plugin's config; `.claude/coddy.yml`, where earlier versions wrote it, is read while `.coddy.yml` is absent, `issue.sh status` prints which as `config`, and `/coddy:config` offers the move before any other change. `scripts/config.sh` prints it, or the sentinel `NOT_ONBOARDED`; every skill except `onboard` injects it and stops on the sentinel, and the guard does nothing without it. `onboard` instead injects `scripts/detect.sh` (both config paths, remote, whether `jj` and `jq` are installed, default branch, whether the PR check workflow is present, make/npm targets, roadmap, whether `.coddy.yml` is git-ignored, recent commits and branches) to pre-fill the config and ask only for what it could not infer. It writes no config while `jq` is missing, since the guard fails closed without it, or while the GitHub plugin cannot answer `get_me` for a GitHub remote.

**Config schema has three copies.** The annotated schema in `skills/onboard/SKILL.md` is authoritative; `skills/config/SKILL.md` lists the same keys with their validation rules, and `README.md` shows an example; the self-test fails unless all three name the same keys. Adding a key means updating all three, `detect.sh` if it can be inferred, and every skill or script that should read it. `onboard` creates the file; `config` changes single keys afterwards and refuses to switch `worktree` while an issue worktree exists. `onboard` never asks for `guard`, `review_block` or `review_rounds`, and asks `tiers` for the running agent only; `config` sets `guard`, and sets `warn` only on the user's explicit ask.

**Tracker variants stay in the prompts.** Tracker is `github` (GitHub MCP plugin tools) or `jira` (Atlassian MCP plugin tools): MCP tools, not CLIs, so no script reaches either, every tracker read or write is a step in a skill, and `bin/coddy` holds only local mechanics. A step that touches the tracker spells out both variants inline.

**Issue work lives in `.worktrees/<issue>`.** The directory name is the issue id, which is how `ship` and the guard find the issue. `start <issue> <branch> [base-issue]` (`create` in the skills) starts the branch from `default_branch` on the remote, or from the base issue's recorded branch as it stands locally (`/coddy:start <issue> onto <base-issue>`), recording that base in `.git/coddy/<issue>.base`; `issue.sh status` prints it as `bases` and `ship` makes it the PR's `--base`, so a stacked PR shows only its own diff. `issue.sh status` lists only the directories that have a claim lock, so a worktree coddy did not create is never offered to `ship` and stays uneditable. It also prints each claim's owner as `owners` (`me`, another session's id with whether its pid runs, or `unknown` for a marker without one), which `next` reads to set claimed issues aside and `ship` to pick only this session's. Every script resolves the real project root when the session was opened inside a worktree, and `issue.sh status` prints it as `root` for the prompts. `worktree` is `jj` (the default, also when the key is absent) or `git`. A jj workspace has `.jj/` and no `.git/`, so `push` drives it with `jj` and the PR is opened by branch name from the skill.

**`start` order is local first, tracker second.** The worktree is created before the issue is claimed, so a failed fetch or a missing `jj` never leaves an issue In Progress with no branch; `claim` refuses to run without the worktree. A re-claim runs the tracker step again, which is idempotent. For either tracker, `start` reads the issue before the transition and refuses one assigned to someone else, or in progress and not to the caller, naming who has it, on a re-claim too, so a takeover from another machine is caught; on the user's yes it reassigns the issue itself and names who lost it, and `claim` records the result.

**In Progress ends at the PR.** `in progress` means no PR yet: `ship` takes the label off (Jira: In Review) once the PR is open, and `start` on a branch with an open PR assigns the issue without the label, since the PR check reads the assignee, and `claim` records it. `sweep` ends the local side once the worktree's last commit is in `default_branch` on the remote through a merge commit, or as the same patches through a squash or rebase merge (git alone, no tracker, and a worktree still on `default_branch`'s own first-parent line is one with nothing of its own yet) and nothing is uncommitted, and only when its lock does not name another running session.

**Skills must stay model-invocable.** None may set `disable-model-invocation` (the self-test asserts it); each carries a `when_to_use` line of trigger phrases so it fires from plain language as well as `/coddy:<name>`. `ship` is the exception in tone: its `when_to_use` restricts it to explicit asks. Keep frontmatter values free of `: ` and ` #` (unquoted YAML scalars).

Skill flow is `onboard` → `next` → `start <issue>` → `ship`, with `triage` feeding new issues back into the tracker. `start` runs from the claim to a reviewed diff in one command: context, thinking with the user, one plan approval with the tier inside it, then implementer, two hardening passes and the code and security review loop, as sub-agents on the briefs next to it (the main agent follows them itself without sub-agents); re-running it resumes from the latest `<!-- coddy:plan -->` comment and `issue.sh state`, and headless questions are posted as a `<!-- coddy:questions -->` issue comment and answered in later comments. Each skill ends by naming the next command rather than chaining into it, and each states what it must not do (`ship` never merges or fixes failures; `onboard` writes nothing but the config and, when accepted, the PR check workflow).

## Conventions

- A hook blocks only on exit 2; any other non-zero exit is a non-blocking error. Hook paths in `bin/coddy` set `code=2` before `die`.
- `bin/coddy` reads no `CLAUDE_*` variable and names no Claude Code path but the legacy config; anything Claude-specific goes in the shims under `scripts/`.
- A Bash command that exits non-zero fires `PostToolUseFailure`, not `PostToolUse`, so `trip` is registered on both.
- A hook that lets the call through but has something to tell Claude prints `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "additionalContext": "..."}}` and exits 0. It leaves `permissionDecision` out, so the normal permission flow still applies.
- `${CLAUDE_PLUGIN_ROOT}` is expanded in skill bodies and in `allowed-tools`, so skills call scripts by that path.
- Scripts are committed executable (`chmod +x`).
- Skill bodies are terse imperative checklists: `condition → action` guards up top, numbered steps, per-tracker variants as sub-bullets. Match that style rather than writing explanatory prose.
- Commits: `type: summary` (`feat`, `fix`, `chore`).
