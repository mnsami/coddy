# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Claude Code plugin (`coddy`) that is also its own single-plugin marketplace. There is no build step and no dependencies: the deliverable is eight prompt files (`skills/*/SKILL.md`), the six sub-agent briefs `start` delegates to, Claude Code plugin agents whose bodies are portable Markdown any agent can run as a sub-agent prompt (`agents/{context,simplest,implement,harden,review,security}.md`), and the policy file they read first (`skills/start/references/policy.md`), the `coddy` command (`bin/coddy`) and the Claude Code shims under `scripts/` that call it, one hook, two CI templates (`templates/coddy.yml` for GitHub, `templates/coddy.gitlab-ci.yml` for GitLab), and `get.sh`, the installer for other agents and the terminal (`curl … | bash`: clones `main` into `${CODDY_HOME:-~/.coddy}`, or fast-forwards it, and links `bin/coddy` into `${CODDY_BIN:-~/.local/bin}`; `CODDY_REPO_URL` names the repository, which `selftest-core.sh` points at a local bare one).

## Commands

```bash
bash scripts/selftest.sh                    # the shims end to end: both worktree tools, claim, push, guard, tripwire, PR check
bash scripts/selftest-core.sh               # bin/coddy on its CODDY_* inputs alone, with no CLAUDE_* set: root, config paths, guard's ask, config lock, start and ship, the git hooks, `get.sh` and `doctor`
claude plugin validate .                    # manifest + skill frontmatter; its one warning, that CLAUDE.md at the plugin root is not loaded as project context, is expected
claude --plugin-dir . -p "/coddy:next"      # run one skill headless against the working copy
```

Both self-tests build a throwaway repo with a local bare remote; `selftest.sh` adds a stub `gh` for the PR check's run block and a stub `curl` for the GitLab job's script alone and skips the jj leg when `jj` is missing. Run both after any change under `bin/` or `scripts/`. CI's `macos-latest` job runs both under `/bin/bash` 3.2 and is the check that every script parses and runs there. `selftest.sh` asserts the static wiring (the `hooks/hooks.json` table, the `allowed-tools` mirror), but not that Claude Code loads the hooks or runs the skills; check those headless inside an onboarded scratch repo:

- `claude --plugin-dir . -p "start issue 42"` - plain-language trigger. In `-p` the Skill call is denied unless `Skill(coddy:start)` is allowed in settings or via `--allowedTools`.
- `--permission-mode acceptEdits` for edit-guard checks, `--allowedTools Bash` for tripwire checks. Without them the permission layer refuses before any hook runs. For `guard: warn`, have the run quote the hook message back: that is the only proof it reached the model.
- `--plugin-dir` replaces the installed coddy for that run, hooks included, so the installed copy does not need disabling.
- A scratch repo whose `repo` names a repository the GitHub plugin cannot read makes `start` stop at its tracker step: the quick way to see it stop without editing.

Skills act on the project in `$CLAUDE_PROJECT_DIR`, so to exercise one, run `claude --plugin-dir /path/to/coddy` from inside a target project that has (or, for `onboard`, lacks) `.coddy.yml`.

Release = a version bump of `.claude-plugin/plugin.json` through a PR of its own, never a direct commit to `main` (the marketplace installs from it); steps in `RELEASING.md`. `marketplace.json` carries no version. An installed copy only changes after a bump: `claude plugin marketplace update coddy && claude plugin update coddy@coddy`.

## Architecture

**Prompts hold judgment, scripts hold mechanics.** A skill decides what to do (which issue, branch name, commit message, PR body); anything that is a fixed command sequence lives in a script so it is tested once and pre-approved.

**Shared brief rules live in `skills/start/references/policy.md`.** The six briefs open by reading it: edit scope, open questions, out-of-scope ideas, verify, commit, the common Return lines, the severity rubric and finding format, the new-mechanism rule, and the skill map (intent → capability phrase → inline fallback). A skill is routed by what its description says it does, never by name, and only when it is listed for the session; a missing one means the fallback, silently. A new shared rule goes there, not into a brief. Each brief is a plugin agent, `coddy:<name>`, whose frontmatter carries `model: inherit` and fixes its tools: `context`, `simplest`, `review` and `security` list theirs, with no Write, Edit, NotebookEdit or Agent, though all four carry Bash, which a Claude Code build with no Grep or Glob tool needs to search and which can write, and `simplest`, `review` and `security` carry Skill, which reaches a forked skill's tools, so `start` checks the worktree with `mark` around each; `implement` and `harden` list none and inherit every tool. `start` passes `tiers.claude.<tier>` as each spawn's `model`, which the Agent tool takes as an alias alone, so `config` and `onboard` take nothing else there; on a host without the agents it runs a generic sub-agent on the file, or follows it itself. The review and security skills run inside their briefs, by policy.md's rows, never in `start`. The self-test holds every agent to its name, a description naming `coddy:start`, `model: inherit`, its tools and its policy.md line.

**Core and adapter.** `bin/coddy` holds every mechanic and reads no `CLAUDE_*` variable (`selftest-core.sh` asserts it). Its inputs: `CODDY_ROOT`, where root resolution starts (`$PWD` without it; then `git rev-parse --git-common-dir`, keeping the caller's spelling, and `/.worktrees/*` stripped outside git); `CODDY_SESSION` and `CODDY_PID`, what the lock's owner line records and is compared with (a caller naming none is not held to the owner); `CODDY_AGENT_DIR`, the agent's own directory under the root (no agent-dir rules without it); `CODDY_EXEC`, the coddy the git hooks `start` writes run (the path `start` was invoked by without it), absolute, refused when it or any link on the way to its file lies under the root, a worktree of the repository or the directory the call began in; `CODDY_PATH`, set by the git hooks alone, the `PATH` git gave them, which `githook` hands the previous hook; `CODDY_BUDGET`, the seconds `snap` and `trip` give the fingerprint (a whole number, 20 without it), half of them to the admin dirs' check before it, for `selftest-core.sh` to lower; `CODDY_HOOKS`, set to `1` by an adapter whose agent runs `snap` before each shell command (any other value is none): `start` and `claim` then print one `hooks: off` line, with Claude Code's causes, when `snap` left no mark for `CODDY_SESSION` in the last 60 s, and never without it. `scripts/issue.sh`, `config.sh` and `detect.sh` are the Claude Code adapter: shims that map `CLAUDE_PROJECT_DIR`, `CLAUDE_CODE_SESSION_ID` and `CLAUDE_PID` onto those three and set `CODDY_AGENT_DIR=.claude` (and `issue.sh` `CODDY_HOOKS=1`), always, ignoring any inherited `CODDY_*` value (a `.claude/settings.json` `env` reaches hook environments, so an honoured one could move the root or widen the agent dir; the core itself honours `CODDY_*` when called directly), taking `CLAUDE_PROJECT_DIR`, for the Bash-tool verbs (every verb but the hooks, `config.sh` and `detect.sh` included), only when it is absolute and the working directory is it or under it, compared by real path (that same `env` overrides it in the Bash tool's environment, where the skills and the injected commands run; `PWD` cannot be set from there, and a session opened through a symlink has it in the link's spelling while the project dir is the real one), and as it is for the hooks (`guard`, `snap`, `trip`), which Claude Code spawns with the real one while their working directory follows the Bash tool's `cd`, so held to it a `cd` out of the project would resolve a root with no config and switch every guardrail off, and name `trip`'s snapshot by another root than `snap`'s, and dropping every `GIT_*` but `GIT_AUTHOR_*`, `GIT_COMMITTER_*`, `GIT_SSH*`, `GIT_ASKPASS` and `GIT_TERMINAL_PROMPT` (a `GIT_DIR` from that env resolves the root in another repository, where no config is, and every hook exits 0; the identity, the transport and the credential prompt reach no path), and source the core (sourced, so the core's messages name the shim, as the skills' `allowed-tools` do), which is why `hooks/hooks.json` and every `allowed-tools` line stay as they were. `issue.sh` also unsets an inherited `CODDY_EXEC` and `CODDY_BUDGET`, and finds the launcher from its own install path (physical) by Claude Code's layout: `<P>/plugins/cache/<marketplace>/<plugin>/<version>` keeps it at `<P>/plugins/data/<id>/coddy`, `<id>` being `<plugin>@<marketplace>` with every character but `A-Za-z0-9_-` a `-`, so a `--plugin-dir` session, whose data dir is `<plugin>-inline`, has none and never repoints the installed coddy's; it sets `CODDY_EXEC` to it for `start`/`create` when it is executable, and the `SessionStart` hook, on `startup` and `resume` alone (a `/clear` or compact in a session still running an install an update replaced would point it back there), runs `issue.sh link "${CLAUDE_PLUGIN_DATA}"`, which has the core's `link` point it at this install's `bin/coddy` when that argument is the derived directory (`-ef`), and does nothing otherwise, printing nothing, since that hook's output is the model's context, and needing no project. Claude Code puts a plugin's `bin/` on the Bash tool's `PATH`, so `coddy <verb>` runs there too; the skills keep calling the shims. That `bin/` is also a ceiling: claude.ai and Cowork do not install a plugin with a top-level `bin/`, through organisation settings either, so coddy needs the Claude Code CLI. The hook JSON (`warn`'s `additionalContext`, the `ask` on `.coddy.yml`) is Claude Code's format, emitted from the core; later adapters translate it.

**Fact injection.** Each skill opens with `` !`bash "${CLAUDE_PLUGIN_ROOT}/scripts/<x>.sh"` `` blocks. These run at skill load and their stdout is inlined into the prompt, so the model starts with config and repo state rather than discovering them with tool calls. The injected scripts (`config.sh`, `detect.sh`) and `issue.sh status` are read-only, print `key: value` lines, and must not fail loudly (`|| exit 0`, `2>/dev/null`, fallback values) since their output is the prompt. The one injected command that is not read-only is `issue.sh sweep` (`next`, `start`): it fetches `default_branch` and removes what a merged branch left behind, prints `cleaned:` and `kept:` lines, and follows the same rule of never failing loudly. Right under the blocks, each skill carries one fallback line for a host that does not inject or expand (the self-test asserts it on every skill, with its read-by-hand command and its variables): a section showing its command rather than its output means run `coddy config`, `coddy sweep` or `coddy status` (`coddy detect` for `onboard`) by hand and read the output as that section; `${CLAUDE_PLUGIN_ROOT}` left unexpanded means the coddy plugin's own install directory, never a `bin/coddy`, `skills/` or `agents/` found inside the project: `coddy <verb>` in the shim's place, and that directory in a path (the briefs and policy.md `start` hands to sub-agents, the template `onboard` reads); `$issue`, `$onto`, `$base` and `$ARGUMENTS` left unexpanded come from the user's request. The `AGENTS.md` block says the same and names the plugin's repository. The line is written without the injection syntax itself, which Claude Code runs anywhere in a line, not only at its start; the self-test asserts no skill carries it inside a line.

The core also unsets `CDPATH`, `TMOUT` and `GREP_OPTIONS` before its first command, for every caller: they act only once it runs a `cd`, a `read` or a `grep`. The layers, all inert until the project is onboarded (the git hooks until `start` installs them, the PR check until its workflow is committed), and `guard`, `snap` and the git hooks refusing rather than inert once the config is removed beside what a started issue leaves (`left`, under Config lock):

- *Edit guard.* `PreToolUse` on Edit/Write/NotebookEdit runs `issue.sh guard`, which rejects (exit 2) any path that is not under `$CODDY_AGENT_DIR/` (`.claude/` from the shims) or inside `.worktrees/<issue>/`, and holds a path inside to that issue's lock (see Lock states); it reads the path as given against the root, then spelled physically against the physical root, found by identity (`-ef`, so macOS's `/System/Volumes/Data` firmlink or a bind mount is the root too), and the stricter result wins, since Claude Code hands the hooks the physical project dir while a path may reach it through a link; the physical spelling is walked a component at a time, each link read from inside its own directory, never onto `/proc` or `/dev/fd` (by identity, so in any spelling, a link's text included), whose magic links the kernel follows to what their text does not name, and a path it cannot follow that way (a `cd` or `readlink` that fails, a step onto `/proc` or `/dev/fd`, more than 40 links, a tail past 4096 bytes or a `..` after a missing directory, a walk past 5 seconds) is refused in both modes, before the mode is read, on the walk that looks for `.coddy.yml` and on the one that holds the edit to its lock. `$CODDY_AGENT_DIR/worktrees/<name>/`, where Claude Code keeps its own worktrees, is the one agent-dir path held to the lock too, in any case of `worktrees`, or an unclaimed edit could hide there. Three refusals hold in both modes, before the mode is read, after the `.coddy.yml` ask: a path with a `.git` or `.jj` component below the root, in any case, as given or where it lands (the main checkout's git dir, a worktree's `.git` file or `.jj/repo`, a submodule's `.git`), a path through macOS's `/.vol`, which names a file by its inode, or under macOS's `/.nofollow` or `/.resolve`, a prefix the kernel strips before it resolves the rest, in any of the guard's readings of it (as given, collapsed by name, walked), and an existing non-directory target with more than one link (a hard link writes every other name of the file too; a `find` that fails refuses), so a hard link to `.coddy.yml` is asked about, not refused. So "In Progress before any code is edited" and "one issue, one worktree" hold even when no skill fired. `.coddy.yml` at the root gets no sensitive-file prompt from Claude Code, so the guard answers it with `permissionDecision: ask` (exit 0), in both modes, by whatever path the write reaches it: its own spelling or one with `./`, `//` or `..`, a relative path (against the hook's `cwd`), a symlink or hard link from a worktree or the agent dir, any case of its name. With `guard: warn` in the config the same check exits 0 and hands Claude the message as `additionalContext` instead, so both rules become advice; any other value, or no key, blocks. Without `jq`, with one that fails or with a payload naming no path, the path cannot be read, so every edit is blocked, in `warn` mode too. A path or `cwd` over 4096 bytes is refused the same way, in both modes, before any work on it: reading one takes time quadratic in its length, and a hook that outlasts its 10 s timeout lets the edit through before Claude Code 2.1.295. The cap bounds the path's length; the walk's own 5 seconds bound its time, since each `cd` costs time in the depth and links repeat steps there. A path or `cwd` with a drive letter (`D:\`, `D:/`, drive-relative `D:x`), a backslash or a leading `//` (UNC and device paths: `//server/share`, `//./D:/`, `//?/D:/`), as native Windows (Git Bash, MSYS2, Cygwin) hands them, or a `cwd` neither empty nor absolute (an object or array included), is refused the same way, in both modes: read as relative, a drive letter or backslash path was held as one under the `cwd` (`$PWD` for an empty one) and passed where that was outside the project, in the agent dir or in a claimed worktree, while the tool wrote the Windows path itself; a leading `//` read as a path outside the project; a `cwd` that was not absolute was refused only by accident (`abspath`'s unset `$2` under `set -u`). Where bash itself runs on native Windows (`$OSTYPE` `msys*` or `cygwin*`) every edit is refused, in both modes, since no path there can be compared with the root (`/proj/x` reads as outside `/c/proj` and lands on `C:\proj\x`, and Windows drops a trailing dot or space or `::$DATA` from `.coddy.yml`). **Lock states.** `claim` makes the lock `.git/coddy/<issue>/` with `mkdir`, so of two sessions claiming at once one wins, and writes its `owner` file: `<CODDY_SESSION> <CODDY_PID> <local start> <start>`, the first two from `CLAUDE_CODE_SESSION_ID` and `CLAUDE_PID`, which Claude Code sets in every shell command's environment and the shims pass on, the last two that process's start time from `ps -o lstart=` in the C locale (spaces as `_`; both empty without `ps`), the third in local time with no suffix, as 0.6.0 wrote it and its `alive` compares it, so a 0.6.0 session still running reads the owner as running, and the fourth in UTC with `_UTC` after it, the one compared here, written only after a third. The editing session is the hook payload's `session_id`. Mine means the same session id or the same pid, since `/clear` changes the id and not the process and `--resume` the process and not the id. A pid counts only while it is the process that started at `<start>`: a reused pid with another start time reads as gone, and a line without a fourth field (0.6.0's, whose third is local), one `ps` cannot check, or one not in that format, falls back to the pid alone. ## Conventions

- A hook blocks only on exit 2; any other non-zero exit is a non-blocking error, and so is a timeout or a hook that cannot start. That is the whole rule for `trip` and `link`. For `guard` and `snap` the EXIT trap in `scripts/issue.sh` turns any other exit of theirs into 2, with a message in plain text that the failure lies in coddy and every such call is refused until the user updates, reinstalls or disables the plugin, so a coddy crash blocks, and their `"onFailure": "block"` in `hooks/hooks.json` makes a timeout (10 s for `guard`, 60 s for `snap`), or a hook that cannot start, block too, from Claude Code 2.1.295; before it those let the call through. When they keep refusing, the ways out are the user's own terminal, `claude plugin disable coddy@coddy` and `claude --settings '{"disableAllHooks": true}'`; on native Windows, or a host without `/usr/bin/env` or `/bin/sh`, where they cannot start, or with no `bash` outside the project, where the launcher refuses every call, the plugin must be disabled from Claude Code 2.1.295 on. Hook paths in `bin/coddy` set `code=2` before `die`.
- `bin/coddy` reads no `CLAUDE_*` variable and names no Claude Code path but the legacy config, the agent dir's `settings.json` and `settings.local.json`, which the fingerprint holds, and, for `doctor`'s `version:`, `.claude-plugin/plugin.json`, the repository's one version source; it names Claude Code's hooks-off causes itself (`disableAllHooks` in a settings file or `--settings`, a managed `allowManagedHooksOnly` without `coddy@coddy` force-enabled, a Claude Code before 2.1.139) in the `hooks: off` line, under `CODDY_HOOKS=1`; anything else Claude-specific goes in the shims under `scripts/`.
- A Bash command that exits non-zero fires `PostToolUseFailure`, not `PostToolUse`, so `trip` is registered on both.
- A hook that lets the call through but has something to tell Claude prints `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "additionalContext": "..."}}` and exits 0. It leaves `permissionDecision` out, so the normal permission flow still applies.
- `${CLAUDE_PLUGIN_ROOT}` is expanded in skill bodies and in `allowed-tools`, so skills call scripts by that path.
- Scripts are committed executable (`chmod +x`).
- Skill bodies are terse imperative checklists: `condition → action` guards up top, numbered steps, per-tracker variants as sub-bullets. Match that style rather than writing explanatory prose.
- Commits: `type: summary` (`feat`, `fix`, `chore`).
