# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Claude Code plugin (`coddy`) that is also its own single-plugin marketplace. There is no build step and no dependencies: the deliverable is six prompt files (`skills/*/SKILL.md`), the bash scripts they call, one hook, and one workflow template (`templates/coddy.yml`).

## Commands

```bash
bash scripts/selftest.sh                    # scripts end to end: both worktree tools, claim, push, guard, tripwire, PR check
claude plugin validate .                    # manifest + skill frontmatter; its one warning, about this CLAUDE.md, is expected
claude --plugin-dir . -p "/coddy:next"      # run one skill headless against the working copy
```

`selftest.sh` builds a throwaway repo with a local bare remote, plus a stub `gh` for the PR check's run block alone; it skips the jj leg when `jj` is missing. Run it after any change under `scripts/`. It cannot prove the hooks or skills are wired; check those headless inside an onboarded scratch repo:

- `claude --plugin-dir . -p "start issue 42"` - plain-language trigger. In `-p` the Skill call is denied unless `Skill(coddy:start)` is allowed in settings or via `--allowedTools`.
- `--permission-mode acceptEdits` for edit-guard checks, `--allowedTools Bash` for tripwire checks. Without them the permission layer refuses before any hook runs. For `guard: warn`, have the run quote the hook message back: that is the only proof it reached the model.
- `--plugin-dir` replaces the installed coddy for that run, hooks included, so the installed copy does not need disabling.
- A scratch repo whose `repo` names a repository the GitHub plugin cannot read makes `start` stop at its tracker step: the quick way to see it stop without editing.

Skills act on the project in `$CLAUDE_PROJECT_DIR`, so to exercise one, run `claude --plugin-dir /path/to/coddy` from inside a target project that has (or, for `onboard`, lacks) `.claude/coddy.yml`.

Release = commit straight to `main` (the marketplace installs from it), then bump `version` in `.claude-plugin/plugin.json` as its own commit (`chore: bump to X.Y.Z`). `marketplace.json` carries no version. An installed copy only changes after a bump: `claude plugin marketplace update coddy && claude plugin update coddy@coddy`.

## Architecture

**Prompts hold judgment, scripts hold mechanics.** A skill decides what to do (which issue, branch name, commit message, PR body); anything that is a fixed command sequence lives in a script so it is tested once and pre-approved.

**Fact injection.** Each skill opens with `` !`bash "${CLAUDE_PLUGIN_ROOT}/scripts/<x>.sh"` `` blocks. These run at skill load and their stdout is inlined into the prompt, so the model starts with config and repo state rather than discovering them with tool calls. The injected scripts (`config.sh`, `detect.sh`, `tree.sh`) are read-only, print `key: value` lines, and must not fail loudly (`|| exit 0`, `2>/dev/null`, fallback values) since their output is the prompt. The one injected command that is not read-only is `issue.sh sweep` (`next`, `start`): it fetches `default_branch` and removes what a merged branch left behind, prints `cleaned:` and `kept:` lines, and follows the same rule of never failing loudly.

**`scripts/issue.sh` is the only script that mutates.** `create` makes the worktree, `claim` locks the issue for this session once the skill has moved it to In Progress, `push` commits and pushes, `sweep` removes the worktree, lock, branch record and local branch of an issue whose PR has merged; `guard`, `snap` and `trip` are the hooks. It reads `worktree` and `default_branch` from the config itself, so the jj/git split lives there and nowhere in the prompts.

**The guardrails are enforced by `hooks/hooks.json`, not by wording.** The layers, all inert until the project is onboarded (the PR check until its workflow is committed):

- *Edit guard.* `PreToolUse` on Edit/Write/NotebookEdit runs `issue.sh guard`, which rejects (exit 2) any path that is not under `.claude/` or inside `.worktrees/<issue>/` for an issue whose lock `.git/coddy/<issue>/` exists. `.claude/worktrees/<name>/`, where Claude Code keeps its own worktrees, is the one `.claude/` path held to that same lock check, or an unclaimed edit could hide there. Only `claim` makes that lock (a plain-file marker from before locks still counts until the next `claim` replaces it): `mkdir`, so of two sessions claiming at once one wins, holding an `owner` file with the claiming session's `CLAUDE_CODE_SESSION_ID` and `CLAUDE_PID` (Claude Code sets both in every shell command's environment). The guard reads that `owner` file too: the hook payload's `session_id` is the editing session's `CLAUDE_CODE_SESSION_ID`, and an edit in a worktree whose owner is another session is rejected with the owner named and whether its pid runs, as is one in a worktree whose claim has no `owner` line yet; `/coddy:start <issue>` is the remedy for both. A lock whose pid is the editing session's own `CLAUDE_PID` counts as its own, for the guard and for `claim`: `/clear` changes the session id, not the process. The owner's edit from a new session id or process moves the lock along, as its re-claim does, so a `--resume` leaves no dead pid behind for other sessions to take over. `push` is held to the same owner, so no session commits and pushes another's worktree. So "In Progress before any code is edited" and "one issue, one worktree" hold even when no skill fired. With `guard: warn` in the config the same check exits 0 and hands Claude the message as `additionalContext` instead, so both rules become advice; any other value, or no key, blocks. The tripwire and the config lock do not read the key.
- *Shell tripwire.* A shell command's writes cannot be predicted from its text, so `PreToolUse` on Bash runs `issue.sh snap` and `PostToolUse` plus `PostToolUseFailure` run `issue.sh trip`. They fingerprint the main checkout (every dirty path with its content hash, `default_branch` when it holds commits its remote branch does not, and `HEAD` when it has left `default_branch`; a detached `HEAD` on that branch's own history is where jj leaves a synced checkout and counts as on it) and exit 2 when the command left new lines in that fingerprint. Only additions count, so an undo is quiet. The fingerprint uses paths rather than git status codes because jj colocation turns untracked files into intent-to-add entries by itself.
- *Config lock.* `.claude/coddy.yml` is the off switch for all of the above, so `snap` keeps a copy and `trip` puts it back when a shell command deleted or changed it. A config identical to the one committed at `HEAD` is left alone (a pull of a shared config). Legitimate changes go through the Edit tool (`/coddy:config`), where Claude Code's own sensitive-file prompt asks the user. `trip` keys off the snapshot, never off the config, or a deleted config would silence it.
- *Branch protection.* `onboard` asks whether `default_branch` requires a pull request and, when it does not, says what to set by hand (no MCP tool reads or writes protection). It is the only layer that holds when a command edits, commits and pushes to `default_branch` in one go.
- *PR check.* `templates/coddy.yml`, which `onboard` offers to copy to `.github/workflows/coddy.yml` and to require on `default_branch`, fails a PR that closes no issue, or closes one that is closed or has no assignee (job name `closes a claimed issue`). Open and assigned is the remote invariant from `claim` to the merge, since `ship` removes the `in progress` label the moment the PR opens and the check runs again on every push. Keyed on the closing references rather than the branch name, it is the only layer that ties a PR to its issue for a cloud agent, which never runs coddy and names its own branch. GitHub computes those references only for a PR against its default branch, so on a PR whose base is another branch (a stack) the block falls back to the closing keywords in the PR body and looks each issue up itself. The run block reads owner, repo, PR number, base, default branch and body from `env`, so it is plain shell that the self-test extracts and runs against the stub `gh`.

Known ceilings: the tripwire reports after the fact and does not see background commands or shell writes inside any worktree, unclaimed or another session's, so only the edit guard (Edit/Write/NotebookEdit) and `push` are held to the lock's owner; both hold only when the lock and the caller name a session, so a claim, a hook payload or a push without one (a script run by hand) is not held to it; both trackers are MCP tools, so the lock records the transition the skill made rather than verifying it, and the skill reads the issue before it writes it, so two machines claiming inside the same round trip both succeed; `sweep` tells a merge by ancestry, so a squash or rebase merge leaves its worktree in place until removed by hand; the PR check reads a stacked PR's closing keywords from its body, so a sidebar-only link on a PR against another branch is not seen.

**`allowed-tools` must mirror the commands exactly.** Every injected command, and every `issue.sh` subcommand a skill runs, is repeated in that skill's `allowed-tools` frontmatter as `Bash(bash "${CLAUDE_PLUGIN_ROOT}/scripts/<x>.sh" …)`. Adding, renaming, or re-quoting one without updating that line brings back permission prompts on every skill run.

**Onboarding gate.** `.claude/coddy.yml` in the target project is the plugin's config. `scripts/config.sh` prints it, or the sentinel `NOT_ONBOARDED`; every skill except `onboard` injects it and stops on the sentinel, and the guard does nothing without it. `onboard` instead injects `scripts/detect.sh` (remote, whether `jj` and `jq` are installed, default branch, whether the PR check workflow is present, make/npm targets, roadmap, recent commits and branches) to pre-fill the config and ask only for what it could not infer. It writes no config while `jq` is missing, since the guard fails closed without it, or while the GitHub plugin cannot answer `get_me` for a GitHub remote.

**Config schema has three copies.** The annotated schema in `skills/onboard/SKILL.md` is authoritative; `skills/config/SKILL.md` lists the same keys with their validation rules, and `README.md` shows an example. Adding a key means updating all three, `detect.sh` if it can be inferred, and every skill or script that should read it. `onboard` creates the file; `config` changes single keys afterwards and refuses to switch `worktree` while an issue worktree exists. `guard` is the one key `onboard` never asks for: `config` sets it, and sets `warn` only on the user's explicit ask.

**Tracker variants stay in the prompts.** Tracker is `github` (GitHub MCP plugin tools) or `jira` (Atlassian MCP plugin tools): MCP tools, not CLIs, so no script reaches either, every tracker read or write is a step in a skill, and `issue.sh` holds only local mechanics. A step that touches the tracker spells out both variants inline.

**Issue work lives in `.worktrees/<issue>`.** The directory name is the issue id, which is how `ship` and the guard find the issue. `create <issue> <branch> [base-issue]` starts the branch from `default_branch` on the remote, or from the base issue's recorded branch as it stands locally (`/coddy:start <issue> onto <base-issue>`), recording that base in `.git/coddy/<issue>.base`; `tree.sh` prints it as `bases` and `ship` makes it the PR's `--base`, so a stacked PR shows only its own diff. `scripts/tree.sh` lists only the directories that have a claim lock, so a worktree coddy did not create is never offered to `ship` and stays uneditable. It also prints each claim's owner as `owners` (`me`, another session's id with whether its pid runs, or `unknown` for a marker without one), which `next` reads to set claimed issues aside and `ship` to pick only this session's. Every script resolves the real project root when the session was opened inside a worktree, and `tree.sh` prints it as `root` for the prompts. `worktree` is `jj` (the default, also when the key is absent) or `git`. A jj workspace has `.jj/` and no `.git/`, so `push` drives it with `jj` and the PR is opened by branch name from the skill.

**`start` order is local first, tracker second.** The worktree is created before the issue is claimed, so a failed fetch or a missing `jj` never leaves an issue In Progress with no branch; `claim` refuses to run without the worktree. Claims are exclusive: a re-claim from the owning session keeps the lock, moves it to the session's current id and pid (`/clear` changes the one, `--resume` the other) and `start` runs the tracker step again, which is idempotent; one from another session is refused and names the owner, unless the owner's pid no longer runs, which is taken over on the spot. For either tracker, `start` reads the issue before the transition and refuses one assigned to someone else, or in progress and not to the caller, naming who has it, on a re-claim too, so a takeover from another machine is caught; on the user's yes it reassigns the issue itself and names who lost it, and `claim` records the result. `claim <issue> --take` is the deliberate takeover of another session's lock, which `start` runs only after asking the user, and it is also the only way into a lock that has no `owner` line (a claim in flight, or one that died between its `mkdir` and that line), which every other claim refuses. A marker from before claims were locks (a plain file) still counts as a claim and becomes a lock at the next `claim`.

**In Progress ends at the PR.** `in progress` means no PR yet: `ship` takes the label off (Jira: In Review) once the PR is open, and `start` on a branch with an open PR assigns the issue without the label, since the PR check reads the assignee, and `claim` records it. `sweep` ends the local side once the worktree's last commit is in `default_branch` on the remote through a merge commit (git alone, no tracker: a squash or rebase merge is not seen, and a worktree still on `default_branch`'s own first-parent line is one with nothing of its own yet) and nothing is uncommitted, and only when its lock does not name another running session.

**Skills must stay model-invocable.** None may set `disable-model-invocation` (the self-test asserts it); each carries a `when_to_use` line of trigger phrases so it fires from plain language as well as `/coddy:<name>`. `ship` is the exception in tone: its `when_to_use` restricts it to explicit asks. Keep frontmatter values free of `: ` and ` #` (unquoted YAML scalars).

Skill flow is `onboard` → `next` → `start <issue>` → `ship`, with `triage` feeding new issues back into the tracker. Each skill ends by naming the next command rather than chaining into it, and each states what it must not do (`ship` never merges or fixes failures; `onboard` writes nothing but the config and, when accepted, the PR check workflow).

## Conventions

- A hook blocks only on exit 2; any other non-zero exit is a non-blocking error. Hook paths in `issue.sh` set `code=2` before `die`.
- A Bash command that exits non-zero fires `PostToolUseFailure`, not `PostToolUse`, so `trip` is registered on both.
- A hook that lets the call through but has something to tell Claude prints `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "additionalContext": "..."}}` and exits 0. It leaves `permissionDecision` out, so the normal permission flow still applies.
- `${CLAUDE_PLUGIN_ROOT}` is expanded in skill bodies and in `allowed-tools`, so skills call scripts by that path.
- Scripts are committed executable (`chmod +x`).
- Skill bodies are terse imperative checklists: `condition → action` guards up top, numbered steps, per-tracker variants as sub-bullets. Match that style rather than writing explanatory prose.
- Commits: `type: summary` (`feat`, `fix`, `chore`).
